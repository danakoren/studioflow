# StudioFlow — technical handoff

Class booking, waitlist and credit management for a small boutique studio.
Written to seed a fresh session: everything below was verified against a real
`npm run build`, not recalled.

**Status: deployed to Vercel and live.** The three cron jobs are implemented
and run daily; the specification documents record why (Architecture §1.5,
Detailed Design §4.7).

## 2. Architecture, in one paragraph

Business rules live in **Postgres functions running under row locks**, not in
TypeScript: `book_session`, `cancel_booking`, `mark_attendance`,
`grant_credits`, `create_recurring_sessions`, `__promote_from_waitlist`. Server
Actions are thin orchestrators routed through a five-stage skeleton in
`lib/auth/action.ts` (authenticate → validate → authorize → execute →
revalidate). **RLS is the only real security boundary**; layout guards and role
checks are user-experience affordances that produce clear errors instead of
empty screens. Reads live in `lib/data/*.queries.ts` and carry no ownership
filters — RLS supplies them, so there is no `where user_id = …` to forget.

Two rules worth knowing before editing:

- **`getUser()`, never `getSession()`.** A cookie is client-controlled;
  `getSession()` decodes it without verifying the signature. `scripts/security-audit.sh` greps for this.
- **The service-role client is confined by ESLint.** `lib/supabase/service.ts`
  may only be imported by `app/api/cron/**` and `actions/member.actions.ts`
  (`no-restricted-imports`). Putting privileged code elsewhere fails the build.

## 3. Database

**Migrations `001`–`012`** in `supabase/migrations/`.

> **There is no `psql` and no authenticated Supabase CLI in this environment.**
> All SQL is applied by pasting into the **Supabase dashboard SQL editor**.
> Plan for that: write the file, then hand it over to be run.

Beyond the original 001–009, added while debugging:

| File | Why |
|---|---|
| `010_grants_fix.sql` | 001–009 enabled RLS and granted on **views** but never on **base tables** for `anon`/`authenticated`. Every query 42501'd, surfacing as opaque `{}` errors. |
| `011_service_role_grants.sql` | Same gap for `service_role` — which broke admin account creation. Keeps `credit_ledger` append-only (INV-4) and withholds `DELETE` everywhere. |
| `012_capacity_change_waitlist.sql` | Raising a session's capacity did not promote waitlisted students. Adds `__fill_open_seats` + an `AFTER UPDATE` trigger, and a `BEFORE UPDATE` guard blocking capacity below the booked count. |

**One-off scripts (already applied):**

- `supabase/fix_seeded_auth_users.sql` — `seed.sql` inserted `auth.users` rows by
  hand and left GoTrue's token columns `NULL`, so **every seeded login failed**
  with `500 Database error querying schema` (identically for right and wrong
  passwords). Fixed in `seed.sql` too, so a fresh re-seed is clean.
- `supabase/backfill_stranded_waitlist_seats.sql` — fills seats stranded before
  migration 012's trigger existed.

## 4. Auth model — admin-only account creation

**Public signup has been removed** (product decision).

The important implementation detail: **`registerStudent` was deleted, not
unlinked.** A Server Action compiles to a POST endpoint whose id ships in the
client bundle, so removing `app/register/page.tsx` alone would have taken away
the form while leaving public account creation fully working for anyone
replaying the request. `/register` now 404s and the action is absent from
`.next/static`.

Also removed: `components/auth/RegisterForm.tsx`, the "Create one" link in
`LoginForm`, the `/register` link in `BookingPanel`, and `/register` from the
middleware bounce. **`/register` is deliberately retained** in
`NEVER_REDIRECT_TO` (`lib/auth/redirect.ts`) — the route is gone, so honouring
`?next=/register` would send someone to a 404.

### `createStudent` (`actions/member.actions.ts`)

Lives in that file because ESLint confines the service-role client to it.

- `runAction(..., { roles: ['admin'] })` — session verified and role read
  server-side from `studio_members` **before** the service client is constructed
- role hard-coded `'student'`; the `.strict()` schema **rejects** an injected
  `role` rather than dropping it
- studio taken from the actor's membership, never the payload
- **`email_confirm: true` is load-bearing** — email confirmation is ON in this
  project (`mailer_autoconfirm: false`), so without it the new student could not
  sign in until clicking an email nobody sends
- `must_change_password: true` → forced rotation at `/change-password`
- **compensating `deleteUser` on partial failure**, since the Auth API and
  Postgres cannot share a transaction. Backported to `createInstructor`, which
  had the same orphaned-auth-user bug.

Verified end-to-end: profile row (via the `handle_new_user` trigger) → member
row → `email_confirmed_at` set → sign-in succeeds → duplicate email returns a
specific message. Form is mounted on `/admin` and `/admin/students`.

Roles: **student / instructor / admin**. `/teach` admits instructor **and**
admin (matching `teaches_session()` and `RoleNav`); `/admin` is admin-only.

## 5. Calendar UI

**7-column week grid** (`components/schedule/WeekGrid.tsx` +
`ClassBlock.tsx`) on `/schedule` and `/admin/schedule` above `lg`, with the
day-grouped list retained below that breakpoint.

Deliberately **not** a time-axis grid: at 1–3 classes/day across 07:00–19:00, a
13-hour axis would be ~90% empty space with each class reduced to a sliver too
small to carry its instructor or seat count. Trade-off: relative time is no
longer spatial, so the time is the boldest element in every block.

Features: all seven days always rendered (an empty column is information),
today's column tinted full-height, past classes at 55% opacity, cancelled
classes drop their colour for grey + strikethrough, legend listing only the
class types present that week. Admin variant shows booked/capacity.

### Colour-coding — `lib/design/class-tone.ts`

Five hues: `#b45309` `#15803d` `#a21caf` `#1d4ed8` `#be123c`. **Validated with a
palette validator, not chosen by eye** — three earlier candidate sets failed
(olive↔rose at ΔE 2.6 deuteranopia; emerald↔sky at 14.0 for *normal* vision;
cyan reading as grey).

Assignment maps each `class_types.color` to its **nearest free slot**, walking
the studio's full class-type list ordered by `created_at`:

- **studio-wide, not per-week** — otherwise a class changes colour between weeks,
  destroying the only thing colour-coding is for
- **collision fallthrough** — Vinyasa (`#6366f1`) and Reformer (`#0ea5e9`) are
  both blues in the DB and would otherwise be indistinguishable
- **append-only** — adding a class type never repaints existing ones
- 6th+ type gets neutral grey rather than a generated hue

Guarded by 13 tests in `tests/unit/class-tone.test.ts`.

> **Recorded caveat:** worst colour-blind pair is green↔amber at **ΔE 6.8
> (protan)**, inside the 6–8 band that is only acceptable *with* secondary
> encoding. Every block carries its class name as text and blocks are
> gap-separated, so the condition holds. **If a future layout drops the text
> label, the palette must be re-stepped.**

### Design system — `app/globals.css`

Brand **ocean** palette (`brand-600 #1f7684`) replacing Tailwind's default
indigo across 24 files; the `slate` ramp retuned in place (264 call sites, and
the new values are still a slate). Layered low-alpha shadows, softer radii,
negative heading tracking, motion tokens + keyframes, `--app-header-height`
(shared by the app header and the grid's sticky day headers), and a
`prefers-reduced-motion` guard using `0.01ms` so `animationend` still fires.

Every contrast pair was **computed**. That caught white-on-`emerald-600` at
3.77:1 (fails AA) — the attendance control uses `emerald-700` (5.48:1).

Empty-state illustrations (`components/ui/illustrations.tsx`) paint **only** via
`stroke="currentColor"` attributes and opacity steps — no Tailwind colour
utilities. An earlier version used `fill-brand-50` etc. and rendered as a large
blank box whenever the stylesheet predated the file. Now a missing class
degrades to dark-and-unstyled rather than invisible.

## 7. Deploying to Vercel

Things that will bite, in order:

1. **Root directory is `studio-flow/`**, not the repo root.
2. **Environment variables:** `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_SITE_URL`,
   `SUPABASE_SERVICE_ROLE_KEY`, `RESEND_API_KEY`, `CRON_SECRET`.
   **`NEXT_PUBLIC_SITE_URL` must be changed to the Vercel domain** — it builds
   the auth-callback URL. Add that domain to Supabase's redirect allowlist too.
3. **`/api/cron/*` is implemented** — all three routes exist and are wired in
   `vercel.json`. Each calls `authorizeCronRequest()` (`lib/cron/authorize.ts`)
   before anything else: a constant-time check of the `Authorization: Bearer`
   header against `CRON_SECRET`, failing closed with 503 when that variable is
   unset or still the `.env.example` placeholder. Generate the real value with
   `openssl rand -base64 32`, set it in Vercel, and redeploy — environment
   variables bind at build time. Schedules are daily, staggered 02:00/03:00/04:00
   UTC, because the Vercel Hobby tier allows at most one run per day; the
   reasoning is in Architecture §1.5 and Detailed Design §4.7.
4. **Email has never actually been sent.** Confirmation is ON and Resend is in
   env, but untested. Admin-created accounts bypass it (`email_confirm: true`),
   so nothing is broken today — it matters if password reset is ever wired up.
   While `RESEND_API_KEY` is absent or still the placeholder,
   `dispatch-notifications` deliberately claims nothing and reports
   `skipped`, because each notification allows only three delivery attempts
   and running against a dead mailer would burn the entire queue to `failed`
   permanently. In-app notifications are unaffected. `RESEND_FROM` sets the
   sender identity and needs a domain verified in Resend.

## 8. Known gaps

- **Deferred routes**, nothing links to them so no 404s: `/admin/instructors`,
  `/admin/class-types`, `/admin/rooms`, `/my/history`. Consequence: a fresh
  studio needs its first room and class type inserted via SQL, since
  `/admin/schedule/new` reads them but cannot create them.
- **No rate limiting** anywhere (accepted as risk R1 in the security doc).
- **`RoleNav` is role-primary, not cumulative** — each role gets one list. Admins
  therefore do *not* see their own `/my/bookings` or `/teach` in the header;
  those live in the tile grid at the foot of `/admin`.
- **Seeded logins:** `student1–6.a@test`, `instructor1–2.a@test`,
  `admin.a@test`, all `password123`. Note those `@test` addresses fail the
  strict `emailSchema` (no dotted domain), so the admin form cannot recreate
  them — `signInSchema` deliberately relaxes format validation so they can still
  log in.
- **Leftover test data:** one Prenatal Yoga class on **15 Sept 2026**. It cannot
  be deleted programmatically because migration 011 deliberately revokes
  `DELETE` on `sessions` from `service_role`; cancel it from its admin page.
